# Image Processor API Contract

## Status

Draft. This contract describes the intended boundary between the Go server and the image processor service.

## Purpose

The image processor receives user-uploaded pet images from the Go server, processes them asynchronously, and reports completion or failure back to the Go server.

The processor exists as a separate service partly because the previous local `withoutbg` script had expensive runtime behavior: high model memory usage and repeated cold-start/model-loading cost each time the Go server invoked the script.

## Ownership Boundary

The Go server owns product state:

- users
- guests
- pets
- image ownership
- user-visible image status
- active pet image selection
- final processed image URL/storage key

The image processor owns operational processing state:

- jobs
- attempts
- worker locks
- retry counts
- internal queue state
- processing errors
- intermediate artifacts
- warm image-processing model/runtime state

The Go server must not read or write the processor database directly. The processor must not read or write the Go app database directly.

## Authentication

Internal service-to-service requests use a shared secret:

```http
Authorization: Bearer <IMAGE_PROCESSOR_SHARED_SECRET>
```

This secret is never exposed to browser or mobile clients.

## Suggested Flow

1. Client uploads an image to the Go server.
2. Go server creates a product image record with status `uploaded` or `queued`.
3. Go server submits a processing job to the image processor.
4. Image processor stores an internal job row.
5. Worker claims and processes the job.
6. Image processor calls the Go server completion webhook.
7. Go server updates product-visible image status to `ready` or `failed`.
8. Clients learn status through polling or SSE.

## Submit Job

```http
POST /v1/jobs
Authorization: Bearer <secret>
Content-Type: multipart/form-data
```

Fields:

- `job_id`: stable ID generated by the Go server
- `image_id`: product image ID generated by the Go server
- `user_id`: owner user ID
- `pet_id`: optional pet ID when already known
- `callback_url`: Go server webhook URL
- `image`: original uploaded file

Response:

```http
202 Accepted
```

```json
{
  "job_id": "uuid",
  "status": "queued"
}
```

## Completion Webhook

The image processor calls this endpoint on the Go server.

```http
POST /internal/image-jobs/{job_id}/complete
Authorization: Bearer <secret>
Content-Type: application/json
```

Successful result:

```json
{
  "job_id": "uuid",
  "image_id": "uuid",
  "status": "ready",
  "processed_image_url": "https://...",
  "processed_storage_key": "pets/images/...",
  "width": 1024,
  "height": 1024,
  "content_type": "image/png"
}
```

Failed result:

```json
{
  "job_id": "uuid",
  "image_id": "uuid",
  "status": "failed",
  "error_code": "background_removal_failed",
  "error_message": "processor failed to remove background"
}
```

## Product Image Statuses

These statuses are user-facing and live in the Go app database:

- `uploaded`
- `queued`
- `processing`
- `ready`
- `failed`

## Processor Job Statuses

These statuses are internal to the image processor:

- `pending`
- `leased`
- `running`
- `retrying`
- `succeeded`
- `dead`

The two status sets do not need to match exactly.

## Idempotency

`job_id` should be idempotent. If the Go server submits the same `job_id` twice, the processor should not create duplicate work.
